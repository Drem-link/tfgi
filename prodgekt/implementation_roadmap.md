# Инструкция по реализации: от текущего сервера до полноценной инфраструктуры

> Порядок важен — каждый этап создаёт фундамент для следующего. Не перепрыгивайте вперёд, пока не закрыт предыдущий этап.

## Этап 0 — Фундамент (сейчас, следующие 1-2 месяца)

Прежде чем просить бюджет на что-то новое, нужно довести до идеала то, что уже есть — это ваш аргумент перед руководством.

- [ ] Закрыть текущий инцидент с DiskPressure окончательно
- [ ] Grafana + Zabbix datasource, работающий дашборд дисков — готовый пример для показа руководству
- [ ] Написать короткий отчёт (1 страница): "что было сделано, какую пользу это уже даёт" — с этим документом идти за бюджетом
- [ ] Настроить регулярные бэкапы того, что уже есть (Zabbix DB, Wiki.js данные) на внешний носитель/другой сервер

**Результат этапа:** рабочая демонстрация ценности + обоснование для следующего шага.

---

## Этап 1 — Второй физический сервер (запрос бюджета №1)

Это самый важный первый шаг — без второй машины ничего из "мультикластера" или "HA" физически невозможно.

**Что просить:** один сервер среднего класса — 8+ ядер, 32GB+ RAM, SSD 500GB+. Б/у корпоративный сервер (Dell/HPE) обойдётся ощутимо дешевле нового.

**Что сделать после получения:**
- [ ] Установить ту же ОС (RED OS или совместимую)
- [ ] Присоединить как второй worker-node к текущему кластеру через `kubeadm join`
- [ ] Перенести часть нагрузки (например, Wiki.js) на новую ноду, освободив ресурсы старого сервера
- [ ] Первый раз в жизни увидеть по-настоящему многонодовый кластер вживую

**Результат этапа:** кластер из 2+ нод, распределение нагрузки, первый практический опыт масштабирования.

---

## Этап 2 — Резервное хранилище и бэкапы (параллельно с этапом 1)

- [ ] Поставить **Velero** для автоматических бэкапов состояния кластера (etcd) и PersistentVolumes
- [ ] Настроить расписание бэкапов (ежедневно/еженедельно)
- [ ] Один раз в месяц **реально проверять восстановление** из бэкапа на тестовом окружении — бэкап, который никогда не проверяли, нельзя считать бэкапом

**Результат этапа:** уверенность, что при аварии данные не потеряются.

---

## Этап 3 — CI/CD (запрос: время на изучение, минимум бюджета)

- [ ] Поставить **Gitea** (лёгкий git-сервер) в кластер — внутренний репозиторий для скриптов/манифестов
- [ ] Написать Dockerfile для одного простого внутреннего инструмента (например, скрипт учёта чего-либо)
- [ ] Настроить **Gitea Actions** или простой webhook: пуш в git → сборка образа → деплой в кластер
- [ ] Прогнать полный цикл минимум 5 раз на разных изменениях, пока не станет привычным

**Результат этапа:** первый работающий автоматический пайплайн — ключевой DevOps-навык для резюме.

---

## Этап 4 — Третий сервер + HA control-plane (запрос бюджета №2, ~6-9 месяцев от старта)

Как только два предыдущих этапа станут стабильны и понятны:

- [ ] Получить третий сервер (можно снова б/у, среднего класса)
- [ ] Пересобрать control-plane в отказоустойчивый режим: 3 master-ноды вместо одной (это можно сделать на тестовом стенде параллельно с продом, не ломая рабочий кластер)
- [ ] Настроить **MetalLB** для распределения входящего трафика между нодами

**Результат этапа:** кластер переживает выход из строя одной ноды без простоя — это то, что реально спрашивают на DevOps-собеседованиях.

---

## Этап 5 — Первый филиал на связи (флагманский шаг)

Здесь начинается настоящая ценность для библиотеки как организации, а не только ваш личный рост.

- [ ] Выбрать один филиал-пилот (не самый большой, чтобы риски были ниже)
- [ ] Поставить недорогой мини-ПК/сервер в филиале
- [ ] Настроить WireGuard-туннель между офисами (то, что вы уже частично делали — просто теперь между двумя реальными зданиями, а не домом)
- [ ] Присоединить сервер филиала как ноду к вашему кластеру (или отдельный маленький кластер + Cilium Cluster Mesh, если нагрузка позволяет)
- [ ] Развернуть там первый полезный сервис — например, реплику Wiki.js, доступную из филиала без задержек

**Результат этапа:** первый реальный межфилиальный сервис — то, что можно показать директору как измеримую пользу.

---

## Этап 6 — Централизованное хранилище (после этапа 5)

- [ ] Развернуть **MinIO** в distributed-режиме, минимум на 4 нодах (можно 2 в главном офисе + 2 в филиале)
- [ ] Перенести сканы документов из локальных папок в MinIO
- [ ] Настроить репликацию между площадками

**Результат этапа:** документы доступны из любого филиала, переживают аварию в одном здании.

---

## Этап 7 — Поиск и каталог (флагманский научный проект)

Это самая долгая и сложная часть — закладывайте на неё 6+ месяцев отдельно.

- [ ] Развернуть **PostgreSQL + PostGIS** для геопривязанных данных
- [ ] Настроить **OpenSearch** для полнотекстового поиска (требует больше RAM — сюда как раз пригодится железо с этапа 1-4)
- [ ] Прогнать существующие сканы через OCR (Tesseract/Tika) для извлечения текста
- [ ] Собрать простой веб-интерфейс: карта России + поиск по содержимому документов

**Результат этапа:** ваш главный projects для портфолио — решённая уникальная бизнес-задача, а не типовой туториал.

---

## Этап 8 — GitOps и зрелый DevOps (когда команда/инфраструктура выросли)

- [ ] Внедрить **ArgoCD** — деплой только через git, без ручных `kubectl apply`
- [ ] Настроить полноценный **Prometheus + Thanos + Loki** стек (теперь железо это потянет)
- [ ] Оформить **Terraform**-описание всей инфраструктуры
- [ ] Подготовиться и сдать сертификацию **CKA** (Certified Kubernetes Administrator)

**Результат этапа:** зрелая, поддерживаемая, задокументированная инфраструктура + подтверждённая квалификация.

---

## Как просить бюджет — практический совет

Каждый этап просите **отдельно**, только после видимого результата предыдущего. Формула для руководства: *"вот что мы получили за X рублей на прошлом этапе (конкретная польза), вот что получим на следующем"*. Просить сразу бюджет на всё — верный способ получить отказ; просить поэтапно, с доказанной пользой — реалистичный путь к финансированию.
